# 안드로이드 EPUB 뷰어 — 아키텍처 검토 및 시행계획

**전제 변경**: CrossPoint에서 계승할 것은 **GUI 구성뿐**. 코드 구조·엔진은 백지에서 최적안을 선택한다.
**설계 목표**: ① 사용 시 최대한 가벼울 것 ② 수정·기능 추가가 쉬울 것
**작성일**: 2026-09-22

---

## 0. 결론

> **WebView를 쓰지 않는 네이티브 조판 + 디스크 페이지 캐시**, 그 위에 **Compose로 얇게 얹은 CrossPoint GUI**.
> 줄바꿈 정책만 **교체 가능한 전략(Strategy)** 으로 두어, 1차는 플랫폼 `StaticLayout`으로 빠르게 출시하고 한국어 조판은 나중에 같은 자리에 끼워 넣는다.

이 한 줄이 두 목표를 동시에 만족하는 유일한 조합인 이유:

| 목표 | 왜 이 설계인가 |
|---|---|
| **가볍다** | WebView를 띄우지 않으면 Chromium 렌더러 프로세스와 그 초기화 비용이 **통째로** 사라진다. 조판은 책당 1회, 이후 페이지 넘김은 캐시된 페이지를 그리는 것뿐 → **재조판 0, 1프레임** |
| **수정이 쉽다** | 바꾸고 싶어지는 것(타이포·제스처·테마·설정 항목)이 전부 **평범한 Kotlin 데이터 변환**이라 기기 없이 JVM 단위 테스트로 초 단위 반복 가능. WebView라면 같은 수정이 "브라우저에 CSS/JS를 주입하고 로그로 디버깅"이 된다 |
| **기능 추가가 쉽다** | 확장점 6개를 **인터페이스/데이터로 미리 뚫어 둔다**(§4). 새 설정 1개 = 데이터 1줄, 새 테마 = 토큰 1벌, 새 블록 타입 = 클래스 1개 + 렌더러 1개 |

**핵심 판단**: "가장 가볍게 *만드는*" 길(WebView)과 "가장 가볍게 *쓰는*" 길(네이티브)은 반대 방향이다. 사용자가 요구한 것은 **쓸 때 가벼움**이므로 네이티브가 맞다. 그리고 **GUI는 어느 쪽을 골라도 동일**하므로, GUI 때문에 이 선택이 제약받지 않는다.

## 1. 평가 기준 (측정 가능하게 정의)

"가볍다"와 "고치기 쉽다"를 숫자로 고정하지 않으면 검토가 취향 다툼이 된다.

### 1.1 가벼움 — 성능 예산 (v1 목표치)

| 지표 | 목표 | 측정 방법 |
|---|---:|---|
| APK 크기 (폰트 제외) | **≤ 12 MB** | `bundletool` / Play Console |
| APK 크기 (폰트 번들 포함) | ≤ 22 MB | 〃 |
| 콜드 스타트 → 라이브러리 표시 | **≤ 500 ms** | Macrobenchmark `StartupMode.COLD` |
| 책 열기 (캐시 적중) | **≤ 300 ms** | Macrobenchmark 커스텀 트레이스 |
| 책 열기 (최초 색인, 300KB 챕터) | ≤ 1.5 s (첫 페이지 표시까지) | 〃 |
| **페이지 넘김** | **≤ 16 ms (1프레임)** | `JankStats` / frame timeline |
| 리더 상주 메모리(RSS) | **≤ 120 MB** | `adb shell dumpsys meminfo` |
| 백그라운드 서비스·주기 작업 | **0개** | — |

> 페이지 넘김 16ms는 **재조판을 하지 않을 때만** 달성 가능하다. 이 한 줄이 "조판 1회 + 디스크 캐시" 설계를 강제한다.

### 1.2 확장성 — 수정 난이도 지표

| 작업 | 목표 비용 | 성립 조건 |
|---|---|---|
| 설정 항목 1개 추가 | **데이터 1줄** (UI·저장·마이그레이션 자동) | 선언적 설정 스키마 |
| 테마 1개 추가 | **토큰 1벌** (화면 코드 무수정) | 디자인 토큰 중앙화 |
| 줄바꿈 정책 교체 | **클래스 1개** | `LineBreaker` 전략 인터페이스 |
| 새 블록 타입(표·수식·각주) | **클래스 1개 + 렌더러 1개** | sealed 블록 + 렌더러 레지스트리 |
| 새 포맷(TXT·MD·FB2) | **파서 1개** | `BookSource` 인터페이스 |
| 조판 로직 수정 후 검증 | **기기 없이 < 5초** | 조판 코어가 순수 Kotlin(JVM) |

마지막 항목이 가장 중요하다. **조판 로직을 기기 없이 테스트할 수 있느냐가 유지보수 비용의 대부분을 결정한다.**

## 2. 설계 축별 검토

### 축 1 — 본문 렌더링 기반 【가장 중요】

| 대안 | 페이지 넘김 비용 | 메모리 | 수정 난이도 | JVM 테스트 | 판정 |
|---|---|---|---|---|---|
| **A. WebView + CSS multi-column** | 브라우저 재레이아웃. 챕터 전환 시 특히 무거움 | Chromium 렌더러 프로세스 상주 | CSS/JS 주입으로만 개입. 브라우저가 노출 안 하는 건 **불가능** | ✕ | ✕ |
| **B. Compose `Text` 컴포저블 다수** | 챕터 전체를 컴포즈해야 페이지 경계를 알 수 있음 → 비쌈 | 중간 | 쉬움 | △ | ✕ |
| **C. Canvas + Paint 직접 그리기 (조판 결과 캐시)** | **캐시된 배치를 그리기만** | 현재 페이지 ±1 | 전부 우리 코드 | **◎** | **★ 채택** |

**C 채택 근거**
- 페이지 넘김이 "이미 계산된 글자 위치에 `drawText` 호출"로 축소된다. 16ms 예산 달성의 전제.
- CrossPoint가 380KB RAM MCU에서 동작한 이유가 정확히 이 구조다. 그 규율을 안드로이드로 가져오면 **배터리·발열 이득**이 된다.
- B의 함정: Compose `Text`는 "주어진 폭에 맞춰 그린다"는 도구지 "이 높이에 몇 줄이 들어가나"를 묻기에는 비싼 도구다. 페이지네이션과 궁합이 나쁘다.

> **"WebView 안 쓰면 EPUB CSS 호환성을 잃는 것 아닌가"** — 잃는다. 다만 잃는 것은 플로트·복잡한 표·SVG 필터 같은 **소설·인문서에 거의 안 나오는** 영역이고, 얻는 것은 위 성능 예산 전부다. §8에 호환성 한계를 명시했다.

### 축 2 — 줄바꿈 정책 【1차/2차 분리】

| 대안 | 코드량 | 품질 | 한국어 양쪽정렬 | JVM 테스트 |
|---|---|---|---|---|
| **A. `StaticLayout` 위임** | **거의 0** | 셰이핑·커닝·bidi·하이픈 전부 플랫폼 품질 | ✕ (`INTER_WORD`는 공백만 늘림) | ✕ (Robolectric 필요) |
| **B. 자체 줄 채우기 (`Paint` 측정 + 자체 정책)** | ~600 LOC | 정책을 완전 통제 | **◎** | **◎** |

**결론: 둘 다 만들고, 인터페이스로 갈아끼운다.**

```kotlin
// core-layout (순수 Kotlin, Android 의존 없음)
interface LineBreaker {
    fun breakIntoLines(tokens: List<Token>, width: Float, m: TextMeasurer): List<Line>
}
```
- **v1**: `PlatformLineBreaker`(StaticLayout 위임) — 즉시 출시 가능, 품질 확보
- **v2**: `KoreanLineBreaker`(CrossPoint 알고리즘 이식) — 같은 자리에 끼우면 끝. **위층 코드 무수정**
- 페이지 패킹(줄 → 페이지)은 **어느 쪽이든 순수 Kotlin**이라 항상 JVM 테스트 가능

이렇게 하면 "한국어 조판이 필수인가"라는 질문이 **일정을 막지 않는다.** 나중에 결정해도 된다.

### 축 3 — 페이지네이션 전략

| 대안 | 페이지 넘김 | 총 페이지 수 | 진도 안정성 | 판정 |
|---|---|---|---|---|
| A. 스크롤 (페이지 없음) | — | — | 쉬움 | ✕ (GUI 요구와 불일치) |
| B. 매번 즉석 계산 | 재조판 발생 | 알 수 없음 | 불안정 | ✕ |
| **C. 챕터 단위 사전 조판 + 디스크 캐시** | **그리기만** | 정확 | **콘텐츠 오프셋 기준** | **★ 채택** |

**C의 필수 부속 3가지** (CrossPoint에서 계승 — MCU 제약이 아니라 좋은 설계라서):
1. **점진적 색인** — 첫 페이지 준비되면 즉시 표시, 나머지는 백그라운드. 큰 챕터에서 사용자를 기다리게 하지 않음
2. **콘텐츠 오프셋 기준 진도** — 페이지 번호가 아니라 "몇 번째 글자"로 저장. 화면 회전·폰트 변경·분할화면으로 재조판돼도 **같은 글자로 복귀**
3. **RenderSpec 해시가 캐시 키** — 조판에 영향 주는 설정이 바뀌면 캐시 자동 무효화

### 축 4 — UI 툴킷

| 대안 | 판정 |
|---|---|
| **Compose + Material 3** | **★ 채택.** CrossPoint의 `ThemeMetrics`(80개 수치 토큰)가 Compose 디자인 토큰과 구조적으로 1:1. 화면당 코드가 짧아 수정이 쉬움 |
| View + XML | ✕ 레이아웃 1개당 파일 2개, 테마 변경이 번거로움 |

리더 본문만 예외: **`Canvas`에 직접 그림**(축 1-C). Compose 안의 `Canvas` 컴포저블에서 `drawIntoCanvas { it.nativeCanvas.drawText(...) }`.

### 축 5 — 의존성 정책 【가벼움의 절반은 여기서 갈린다】

"무엇을 안 쓰는가"가 무엇을 쓰는가보다 중요하다.

| 후보 | 채택 | 이유 |
|---|---|---|
| Compose, Material3, Navigation-Compose | ✅ | 필수 |
| Room | ✅ | 라이브러리/진도/북마크. 가볍고 마이그레이션 안전 |
| DataStore(Proto) | ✅ | 설정 |
| Coil | ✅ | 커버 썸네일만 |
| `XmlPullParser`, `java.util.zip` | ✅ | **플랫폼 내장. 0 바이트** |
| **Hilt** | **❌** | 화면 20개 규모에 코드 생성·빌드시간·APK를 지불할 이유 없음 → **생성자 주입 + `AppContainer` 수동 DI** |
| **Readium kotlin-toolkit** | **❌ (보류)** | 이전 검토에서는 "M0 1~2주 단축"을 이유로 권장했으나, **목표가 '가장 가볍게'로 바뀌면 판단이 뒤집힌다.** Publication/Resource/Fetcher 추상화 + 의존 그래프를 로컬 EPUB 뷰어가 짊어질 이유가 없다. 자체 파서는 **~1,200 LOC**이고 전부 우리가 통제 가능. → **EPUB 엣지케이스가 실제로 문제가 되면 그때 도입** |
| **WebView** | **❌** | 축 1 결론 |
| Retrofit / OkHttp | ❌ (v1) | v1에 네트워크 없음 |
| epub4j / epublib | ❌ | 자체 파서로 충분, 의존 추가 대비 이득 없음 |

> **이전 계획서(`ANDROID_BASE_CANDIDATES.md` §4 안 1)에서 Readium 채택을 권했던 것을 철회한다.** 그때의 목표는 "M0 단축"이었고, 지금의 목표는 "가장 가볍고 고치기 쉬울 것"이다. 목표가 바뀌면 답이 바뀌는 것이 정상이며, 바뀐 이유를 남긴다.

## 3. 권장 아키텍처

```
┌──────────────────────────────────────────────────────────┐
│ :ui                Compose 화면 20개                       │
│                    (CrossPoint GUI 이식 — §5)              │
├──────────────────────────────────────────────────────────┤
│ :ui-design         CpTheme: 토큰 + 컴포넌트 10개            │
├──────────────────────────────────────────────────────────┤
│ :reader-render     Canvas 그리기 · 제스처 · 페이지 애니메이션 │
│                    ← Android 의존                          │
├──────────────────────────────────────────────────────────┤
│ :text-platform     TextMeasurer(Paint) 구현                │
│                    PlatformLineBreaker(StaticLayout) 구현  │
│                    ← Android 의존이 여기서 끝난다           │
├══════════════════════════════════════════════════════════┤
│ :core-layout       ★ 순수 Kotlin / JVM — Android 의존 0     │
│                    블록 모델 · CSS 적용 · 줄바꿈 인터페이스   │
│                    · 페이지 패킹 · 페이지 직렬화             │
│                    → 전부 JVM 단위 테스트                   │
├──────────────────────────────────────────────────────────┤
│ :epub              ZIP · OPF · NCX/NAV · CSS 서브셋 파서     │
│                    (순수 Kotlin + XmlPullParser)           │
├──────────────────────────────────────────────────────────┤
│ :data              Room · DataStore · SAF · 페이지 캐시 파일 │
└──────────────────────────────────────────────────────────┘
```

**설계 원칙 3개**

1. **Android 의존을 `:text-platform` 아래로 내려보내지 않는다.** `:core-layout`과 `:epub`이 순수 Kotlin이면, 조판 버그를 기기 없이 5초 만에 재현·수정·검증할 수 있다. 이 하나가 유지보수 비용의 대부분을 결정한다.
2. **책 전체를 메모리에 올리지 않는다.** 상주하는 것은 현재 페이지 ±1과 현재 챕터의 페이지 오프셋 표뿐.
3. **조판은 1회, 이후는 그리기.** 페이지 넘김 경로에 계산을 넣지 않는다.

## 4. 확장점 설계 — "기능 추가가 쉽다"의 구체화

추상화는 미리 뚫어 둔 곳에서만 값이 싸다. 아래 6개만 뚫고 나머지는 평범하게 쓴다.

### 4.1 줄바꿈 정책
```kotlin
interface LineBreaker { fun breakIntoLines(...): List<Line> }
// PlatformLineBreaker (v1) / KoreanLineBreaker (v2) / VerticalLineBreaker (세로쓰기, 미래)
```
**추가 비용: 클래스 1개.** 위층 무수정.

### 4.2 설정 스키마 (선언적)
CrossPoint `SettingsList.h`의 방식을 그대로 계승 — 설정을 **코드가 아니라 데이터로** 정의하면 UI·저장·마이그레이션이 자동으로 따라온다.
```kotlin
val SETTINGS = listOf(
    Setting.Enum(key="lineSpacing", category=READER, titleRes=…, values=…, default=1),
    Setting.Range(key="margin", category=READER, min=5, max=40, step=5, default=15),
    Setting.Bool (key="paragraphIndent", category=READER, default=false),
)
```
**추가 비용: 1줄.** 설정 화면·DataStore 스키마·RenderSpec 해시가 전부 자동 반영.

### 4.3 디자인 토큰
```kotlin
@Immutable data class CpMetrics(/* 80개 수치 */)
val LocalCpMetrics = staticCompositionLocalOf { CpMetrics.Lyra }
```
**테마 추가 비용: 토큰 1벌.** 화면 코드 무수정.

### 4.4 블록 타입 (sealed + 렌더러 레지스트리)
```kotlin
sealed interface Block { data class Text(…); data class Image(…); data class Rule(…) }
fun interface BlockRenderer<T: Block> { fun draw(b: T, c: Canvas, o: Offset) }
```
**표·수식·각주 박스 추가 비용: 클래스 1개 + 렌더러 1개.**

### 4.5 포맷
```kotlin
interface BookSource {           // EPUB / TXT / MD / FB2 …
    suspend fun metadata(): BookMeta
    suspend fun spine(): List<SpineItem>
    suspend fun content(i: Int): Reader
}
```
**추가 비용: 파서 1개.** 조판·리더·라이브러리 전부 재사용.

### 4.6 리더 오버레이 슬롯
페이지 위에 겹치는 레이어(북마크 표시, 하이라이트, TTS 진행, 사전 툴팁)를 **슬롯 리스트**로 둔다.
```kotlin
interface ReaderOverlay { @Composable fun Content(page: PageState) }
```
**기능 추가 비용: 오버레이 1개.** 리더 본체 무수정.

## 5. GUI 이식 명세 — CrossPoint에서 가져오는 유일한 것

좋은 소식: **GUI는 컴포넌트 10개로 끝난다.** `BaseTheme`의 그리기 API 표면이 곧 부품 목록이었다.

| # | 컴포넌트 | CrossPoint 원형 | 안드로이드 각색 |
|---|---|---|---|
| 1 | `CpHeader` | `drawHeader` | 제목 + 부제. 상단 |

**각색 원칙**:
- 원본 수치는 **480×800 e-ink 기준**이므로 그대로 dp로 옮기지 않는다. 비율로 재해석하되 **터치 타깃 48dp 하한**을 강제
- 5단계 흑백 디더 → **Light / Dark / Sepia** 팔레트로 승격
- 1bit 아이콘 16종 → **벡터 재작성**
- 화면 구성(무엇이 어디 있는가)은 **그대로 유지**. 이것이 사용자가 마음에 들어 한 부분

## 6. 가벼움을 지키는 규칙 (코드 리뷰 체크리스트로 사용)

1. **페이지 넘김 경로에 측정·할당·I/O를 넣지 않는다.** 위반 시 16ms 예산 붕괴
2. **책 전체를 메모리에 올리는 API를 만들지 않는다.** 항상 챕터 단위 스트리밍
3. **의존성 추가는 APK 증가분과 함께 PR에 기재한다.** 100KB 이상이면 근거 필요
4. **백그라운드 서비스·WorkManager 주기 작업 금지** (v1). 조판은 앱이 앞에 있을 때만
5. **이미지는 `inSampleSize`로 뷰포트 크기까지 줄여 디코드.** 원본 해상도 비트맵 금지
6. **리플렉션·어노테이션 프로세서를 늘리지 않는다.** 빌드 시간 = 수정 비용
7. **Macrobenchmark를 CI에 넣고 예산 초과 시 실패시킨다.** 숫자가 없으면 "가볍다"는 주장일 뿐

## 8. 명시적 한계 (미리 합의할 것)

네이티브 조판을 고른 대가로 **v1에서 지원하지 않는 것**:

| 항목 | 상태 | 비고 |
|---|---|---|
| 복잡한 표 (병합 셀·중첩) | 단순 표만 | 소설·인문서에 거의 없음 |
| CSS float / position | ✕ | |
| SVG 본문 삽화 | ✕ | 래스터 이미지는 지원 |
| 미디어 오버레이 (읽어주기 동기화) | ✕ | |
| 고정 레이아웃 EPUB (만화·그림책) | ✕ | 리플로우 전용 |
| 세로쓰기 | ✕ | `LineBreaker` 확장점으로 향후 가능 |
| PDF | ✕ | 원본도 out-of-scope |

이 목록이 수용 불가라면 **축 1을 WebView로 되돌려야 하고**, 그 순간 §1.1의 성능 예산은 전부 재설정된다. 둘 다 갖는 방법은 없다.
